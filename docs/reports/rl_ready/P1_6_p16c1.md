# P1-6 cycle p16c1: alias_free_v2

Proposed by the external agentic optimizer (P1-6) and accepted by the frozen evaluator of the baseline.

## Problem and bottleneck evidence

Workload A (batched_headless, s512, control steps 229-238 = tool contact and cutting) at N=8 is GPU-bound: kernel time 2781 us per substep against a step wall of 2.86 ms per substep (0.572 s per 200-substep control step). The particle-particle contact kernel of alias_free_v1 (_particle_contacts_skip_zero_b) is the largest stage: 988 us per substep = 35.5 % of kernel time, then p2g 690 us (24.8 %), musl 302 us (10.9 %), and the 64-bit CUB radix sort of the grouped hash build 98.5 us (3.5 %) (nsys --cuda-graph-trace=node, 10 control steps, nsys/ref_n8/). Per env the contact kernel costs 123 us at N=8 against about 111 us at N=1: the grouped wp.HashGrid query performs two binary searches over the (cell, env) keys of every visited cell (27 cells per particle) to find its env's range, and that range search grows with N. All 27 cells of the 2.4 r box are visited although a non-zero pair impulse needs d < 2r + 2 dt v_max (recorded particle speeds stay below 0.13 m/s).

Hypothesis: Two Level A changes to how the alias-free contact query enumerates candidates remove work that never produces a contribution. (1) Env-major buckets (analysis C4): key env*C + cell on the alias-free dims, sorted by a stable radix sort over ceil(log2(N*C)) = 23-24 bits instead of 64-bit grouped keys, bucket bounds validated by the sorted key instead of a memset; the kernel reads a bucket with 3 loads and no binary search, and the sort needs 3 passes instead of 8. (2) Per-env query shrink (analysis C3): while every particle of an env is slower than V = 0.25 m/s the query reach is (2r + 2 dt V)(1+1e-5) + 1e-7 m = 0.95 mm instead of 2.4 r = 1.08 mm, so on average about 2.76^3 = 21 instead of 27 cells are visited. The contact kernel should drop by about half and the sort by about half; the other stages are unchanged, so env-steps/s rises by roughly the contact share removed, and more at larger N because the removed binary searches grow with N.

## Change

- Variant (opt-in): `{"particle_contact_mode": "alias_free_v2"}`; default behaviour unchanged: True
- Rollback: particle_contact_mode='alias_free_v1' (or the default 'frozen_v1'); both code paths are untouched and byte-identical in behaviour. Inside v2, particle_contact_options={'shrink_speed_m_s': None} turns the query shrink off (env-major buckets only).
- Parity level A: Same contributions, same per-particle candidate order, same float operations (P1-3 analysis section 2, level A given a certificate). Env-major buckets: the key uses Warp's own hash_grid_index arithmetic and float32 cell_width_inv, the sort is stable over ascending particle ids, and the kernel walks cells x fastest, then y, then z with Warp's x_end clamp, so every particle visits exactly the candidate sequence of hash_grid_query(grid, x_p, 2.4 r, e) on the grouped alias-free grid (CPU test: identical id sequences against a grouped wp.HashGrid for dims (5,5,5), (64,64,32), (7,3,4), also after a rebuild on moved points, which exercises the memset-free key validation). Query shrink: a pair impulse is non-zero only if d - 2r + dt*min(v_rel.n, 0) < 0, i.e. d < 2r + dt|v_rel| <= 2r + 2 dt V when both speeds are <= V; such q lie inside the shrunken box (relative 1e-5 and absolute 1e-7 m slack cover float32 rounding), whose cells are a sub-box of the frozen box since floor is monotone, so the visited candidates form an order-preserving subsequence and every dropped candidate contributes exactly zero, which C1 already skips (a +-0 add is the identity on the impulse). The per-env speed flag is computed every substep in the existing guard pass; a flagged env (any particle faster than V or non-finite) uses the frozen reach. Envs failing the alias certificate still go to the unchanged frozen fallback. CPU evidence (Warp CPU, np.array_equal on every array after every substep against the frozen single solver): heterogeneous block scenes at frozen and forced 5x5x5 aliasing dims with >= 2 non-zero contributions per particle, a full-resolution TRIM substep, an N=3 heterogeneous TRIM cutting sequence, partial reset against frozen_v1, and a necessity test: env particles at 20 m/s stay bitwise with the check, and differ when the speed check is disabled while the shrunken reach is kept. GPU dev: samestate reruns bitwise, s512 N=1 full episode final labels identical to alias_free_v1 (37958 labelled, 332 positive), no guard violations, invalid_reason 0.

## Limitations

- VRAM peak and reset p95 are measured inside the process under test (candidate-reported, not independently verified); env-steps/s comes from the caller's outer clock and is cross-checked against the in-process value
- intermediate Native-sample positions are dumped as int8 micrometre deltas to the Native sample (|error| <= 0.5 um, larger or non-finite deltas exact); final states are exact
- the evaluator reference arrays (mass, reference positions, stencils) are taken from the WP-17 Native recording
- samestate uses the baseline harness helpers (run_p1_3a.load_state / contact_stage) on the solver attributes x, v, code, impulse, stats_sum, stats_max, hash / particle_contact
- workload A is reduced fidelity (ideal edge tracking, no robot dynamics, reaction not fed back)
- G9:window is measured on the episode-mode runs of the window_check plans (same variants, same seeds, replay from reset), not inside the G9 throughput processes; it gates tool-material contact steps (stats slot 1) and new labels, particle-particle contacts (slot 4) are reported only
- performance.phases are in-process step walls (candidate-reported), descriptive only
